Module Marketing — Phase 5 : Fidélisation (Promotions, Coupons, Récompenses,
 Gamification, Parrainage)

 Contexte

 Les Phases 1 (Core), 2 (Communication), 3 (Content & Social Media) et 4
 (Automation) sont livrées et déployées (dev + prod Neon). Cette Phase 5 couvre
 le CDC §32-37 (Promotions/Coupons/Fidélisation/Gamification) + le hub
 "Parrainage" (§2, structure de données §84 :
 marketing_referral_programs/marketing_referrals).

 Constat majeur de l'audit — deux briques entières existent déjà et ne doivent
 pas être dupliquées :
 - Promotion (modèle + moteur, Catalogue §9) est déjà 100% construit :
 app/api/admin/catalogue/promotions/{route.ts,[id]/route.ts} (CRUD complet,
 lib/promotionValidation.ts::validerPromotion()),
 lib/promotions.ts/lib/promotionsServer.ts (résolution + calcul de remise), et
 déjà appliqué automatiquement à la vente via lib/venteTarification.ts →
 prixPromotionnel() (consommé par Ventes/Caisse/Crédit, cf. mémoire
 catalogue-branchement-flux-vente). C'est exactement ce que le §32 demande ("le
 moteur commercial existant applique ensuite les règles de vente") — déjà vrai
 aujourd'hui. Il ne manque qu'une surface Marketing (menu, lien vers la
 campagne) — pas un nouveau moteur.
 - RecompenseFidelite (catalogue de récompenses :
 nom/type/coûtPoints/valeur/produit/expiration, enums
 TypeRecompense/StatutRecompense) existe déjà en base mais n'est référencé
 nulle part dans le code applicatif (0 résultat sur RecompenseFidelite hors
 schéma) — modèle orphelin, jamais branché. Sa table de rachat
 UtilisationRecompense pointe vers PointsFidelite (le grand livre legacy,
 confirmé mort en Phase 2 — la source de vérité active est CompteFidelite/Trans
 actionFidelite/lib/fidelite.ts::attribuerPointsFidelite()). Décision :
 réutiliser RecompenseFidelite tel quel comme catalogue, mais créer une
 nouvelle table de rachat branchée sur CompteFidelite (la legacy
 PointsFidelite/UtilisationRecompense reste intouchée, comme toujours dans ce
 chantier).
 - Rien n'existe pour : Coupons (commentaire déjà présent dans le schéma : //
 Coupon (Phase 5 Fidélisation) n'existe pas.), Gamification
 (challenges/badges/classement), Parrainage.

 Principe directeur (§85, redit dans ce nouveau passage du CDC) : le marketing
 ne duplique rien.

 Décisions de conception (scope assumé)

 - Promotions & Offres (§32-34) = surface Marketing fine sur le moteur
 existant, pas un nouveau CRUD. Ajout additif Promotion.campagneId Int? (même
 pattern que VenteDirecte.campagneId/CreditClient.campagneId en Phase 1) pour
 l'attribution CA à une campagne ; validerPromotion() étendu pour l'accepter.
 Nouvelle page /dashboard/admin/marketing/promotions qui consomme les endpoints
 /api/admin/catalogue/promotions existants (GET/POST/PATCH), rien de nouveau
 côté API sauf le champ campagneId.
 - Coupons (§35) = nouveau, mais volontairement scoping restreint à la vente
 admin (app/api/admin/ventes) pour cette phase : le code coupon est appliqué au
 niveau du panier (remise sur montantTotal), pas ligne par ligne comme les
 promotions. Câbler Caissier/RPV/Agent terrain (3 routes de création de vente
 distinctes, aucune fonction partagée entre elles — confirmé à l'audit) est une
 extension triviale du même appel une fois le pattern validé, explicitement
 différée — pas la peine de gonfler cette phase déjà chargée pour un besoin non
 confirmé sur les 3 autres surfaces.
 - Fidélisation avancée (§36) = catalogue RecompenseFidelite (réutilisé) +
 nouvelle table de rachat RecompenseEchange branchée sur CompteFidelite,
 dépense de points via attribuerPointsFidelite(tx, {type:"DEPENSE", ...})
 (fonction déjà existante, Phase 4). Pas d'auto-service client (aucune appli
 client n'existe dans ce codebase, cf. mémoire catalogue "reste = appli
 mobile") — le rachat est déclenché côté staff (marketing/agence) sur la fiche
 d'un client, comme tout le reste du module.
 - Gamification (§37) = objectif quantifiable minimal fidèle à l'exemple unique
 du CDC ("achetez 5 fois ce mois-ci") : NB_ACHATS ou MONTANT_ACHATS sur une
 période, pas de moteur de règles générique. Badges = attribution automatique
 sur condition simple (niveau de fidélité atteint, ou nb d'achats total) — pas
 de système de règles composables (aurait démesurément gonflé le scope, même
 raisonnement qu'en Phase 4 pour la condition d'arrêt). Classement = requête de
 lecture agrégée sur CompteFidelite.totalGagnes (déjà la donnée qui existe),
 pas un nouveau modèle de score.
 - Parrainage = structure simple confirmée par le CDC lui-même (§84 : seulement
 2 tables marketing_referral_programs/marketing_referrals) : un parrain
 (Client), un filleul (Client, un seul parrain possible), qualification =
 premier achat du filleul (réutilise le même principe de détection que
 PREMIER_ACHAT en Phase 4), récompense en points aux deux via
 attribuerPointsFidelite. Saisie du code parrain scopée à la création client
 côté admin (app/api/admin/clients POST) pour cette phase, même logique
 d'extension différée que les coupons.
 - Évaluation planifiée (qualification parrainage, progression challenges,
 attribution badges) = nouveau cron dédié /api/cron/marketing/fidelisation
 (même gabarit ?secret=CRON_SECRET que alertes/marketing/automatisation),
 distinct du cron Automation (Phase 4) pour rester lisible — ce n'est pas le
 même domaine fonctionnel.
 - RBAC : aucun nouveau module, réutilise "marketing" (déjà branché Phases
 1-4). Aucun nouveau rôle.

 Logique métier

 - lib/coupon.ts : genererCodeCoupon() (si non fourni), validerCoupon(code,
 ctx: {clientId, pointDeVenteId, produitIds}) → vérifie actif/fenêtre de
 dates/agence/produit/audience (réutilise AudienceMarketingMembre si audienceId
 renseigné)/plafond global/déjà utilisé par ce client, appliquerCoupon(tx,
 {couponId, clientId, venteId, montantAvant}) → calcule la remise (réutilise la
 logique POURCENTAGE/MONTANT de lib/promotions.ts::appliquerPromotion, adaptée
 au panier) + crée CouponUtilisation. Câblé dans app/api/admin/ventes/route.ts
 (accepte couponCode optionnel dans le body).
 - lib/recompensesFidelite.ts : echangerRecompense(tx, {clientId, recompenseId,
 creeParId}) → vérifie actif/dateExpiration/solde suffisant
 (CompteFidelite.soldePoints >= coutPoints), dépense via
 attribuerPointsFidelite(tx, {type:"DEPENSE", points:-coutPoints,
 source:"RECOMPENSE"}), crée RecompenseEchange (statut DISPONIBLE). Action
 distincte pour marquer UTILISEE (remise physique confirmée par le staff).
 - lib/gamificationMarketing.ts : evaluerChallenges() — pour chaque
 ChallengeMarketing ACTIF dans sa fenêtre, calcule la progression par client
 (count/sum VenteDirecte filtré statut notIn [ANNULEE,BROUILLON] depuis
 dateDebut, même filtre que Phase 4), upsert ParticipationChallenge, attribue
 les points + marque REUSSI au franchissement du seuil (une seule fois,
 @@unique protège l'idempotence). evaluerBadges() — scanne les conditions
 simples (niveau CompteFidelite.niveau, ou total achats) et crée BadgeClient si
 absent.
 - lib/parrainage.ts : evaluerParrainagesQualifies() — pour chaque Parrainage
 EN_ATTENTE, vérifie si le filleul a un premier achat (VenteDirecte valide) →
 passe QUALIFIE → attribue les points aux deux (attribuerPointsFidelite ×2) →
 passe RECOMPENSE. Génération de codeParrainage à la création client
 (app/api/admin/clients POST) : si codeParrainageUtilise fourni dans le body,
 résout le Client parrain correspondant et crée le Parrainage (EN_ATTENTE).
 - app/api/cron/marketing/fidelisation/route.ts : orchestre evaluerChallenges()
 + evaluerBadges() + evaluerParrainagesQualifies(), même gabarit CRON_SECRET
 que les crons existants. Entrée vercel.json (nouveau créneau, ex. 0 9 * * *).
