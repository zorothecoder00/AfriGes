 Module Marketing — Phase 1 : Marketing Core

 Contexte

 AfriSime a fourni un cahier des charges de 89 sections pour un module
 Marketing global (Acquisition, Communication, Promotion, Fidélisation,
 Animation commerciale, Data Marketing, Analyse, Automatisation). Le principe
 directeur (§85-86, 89) est strict : le marketing ne recrée rien — il consomme
 en lecture les données déjà gérées par les modules existants (CRM/Client,
 Ventes, Stock, Crédit, Comptabilité, Agences) pour piloter par-dessus :
 campagnes, audiences, budgets, communication, automatisation.

 Le CDC lui-même découpe le développement en 7 phases (§88) pour éviter de tout
 coder simultanément. Ce plan couvre uniquement la Phase 1 — Marketing Core :
 campagnes, types de campagne, objectifs, brief marketing,
 segmentation/audiences (statique/dynamique/RFM), budgets, KPI (dashboard
 global + par agence), hiérarchie marketing, canaux (référentiel), et le
 branchement RBAC/navigation. Les phases 2-7 (Communication, Content/Social,
 Automation, Fidélisation, Terrain/Événementiel, Analytics/IA) ne sont pas dans
 ce lot — les modèles posés en Phase 1 sont conçus pour qu'elles s'y
 raccrochent sans reprise de schéma.

 Audit du code existant déjà fait (voir échanges précédents) :
 RESPONSABLE_MARKETING existe déjà dans l'enum RoleGestionnaire mais n'a aucun
 droit RBAC ni menu. Aucun modèle Campagne/Audience/Coupon n'existe. Des
 briques réutilisables existent (Promotion, Tag/ClientTag, CompteFidelite,
 EligibiliteClientRIA) — consommées en lecture, jamais dupliquées.

 Décisions de conception validées avec l'utilisateur

 - Attribution du CA (§56-57) : ajout d'un champ nullable campagneId sur
 VenteDirecte et CreditClient (tagging à la saisie). Changement additif, non
 cassant, sur 2 modèles centraux existants.
 - Nommage des modèles : PascalCase français (Campagne, AudienceMarketing,
 BudgetMarketing…), cohérent à 100 % avec l'existant (CreditClient,
 PointDeVente…) — pas les noms marketing_campaigns etc. du §84, qui n'étaient
 qu'une illustration conceptuelle en anglais/snake_case.
 - Types de campagne (§7) et canaux (§21+) : tables paramétrables sans code
 (§81), pas des enums Prisma figés — un admin/responsable marketing doit
 pouvoir en ajouter depuis l'UI.
 - Objectifs de campagne (§8) : liste fixe métier (8 valeurs) → enum Prisma,
 avec table pivot pour le multi-objectif (§8 : "une campagne peut avoir
 plusieurs objectifs").
 - Audiences (§10-15) : moteur de règles simple (combinables en ET pour la V1,
 pas d'arbre OR/ET complexe), matérialisé dans une table de membres pour
 lecture uniforme, recalculé pour les dynamiques, figé pour les statiques.
 - Portail : mono-page à onglets (patron responsablesPointDeVente/chefAgence)
 pour RESPONSABLE_MARKETING, + entrée admin globale pour la Direction (§4 :
 Direction voit tout, responsable d'agence voit son agence).

 Campagne (§6) — cœur du module :
 prisma
 model Campagne {
   id           Int             @id @default(autoincrement())
   code         String          @unique   // ex CAMP-2026-0001, auto-généré
   nom          String
   description  String?
   statut       StatutCampagne  @default(BROUILLON)
   portee       PorteeCampagne  @default(AGENCE)

   responsableId Int
   responsable   User            @relation("CampagneResponsable", fields:
 [responsableId], references: [id])
   commercialId  Int?            // §5 marketing commercial : action portée par
 un commercial précis
   commercial    User?           @relation("CampagneCommercial", fields:
 [commercialId], references: [id])

   typeCampagneId Int
   typeCampagne   TypeCampagne   @relation(fields: [typeCampagneId],
 references: [id])

   // Brief marketing (§9)
   brief          Json?          // { probleme, cible, message, offre, zone,
 resultatAttendu }

   audienceId     Int?
   audience       AudienceMarketing? @relation(fields: [audienceId],
 references: [id])

   dateDebut      DateTime
   dateFin        DateTime

   budget         BudgetMarketing?
   objectifs      CampagneObjectif[]
   agences        CampagneAgence[]
   produits       CampagneProduit[]
   canaux         CampagneCanal[]
   depenses       DepenseMarketing[]
   ventesAttribuees    VenteDirecte[]   @relation("VenteCampagne")
   creditsAttribues    CreditClient[]   @relation("CreditCampagne")

   creeParId    Int
   createdAt    DateTime @default(now())
   updatedAt    DateTime @updatedAt

   @@index([statut])
   @@index([dateDebut, dateFin])
   @@index([responsableId])
 }

 model CampagneObjectif {
   campagneId Int
   objectif   ObjectifCampagneType
   campagne   Campagne @relation(fields: [campagneId], references: [id],
 onDelete: Cascade)
   @@id([campagneId, objectif])
 }

 model CampagneAgence {
   campagneId     Int

 [id], onDelete: Cascade)

 [id])

 model CampagneProduit {
   campagneId Int
   produitId  Int?
   familleId  Int?

   famille    FamilleProduit? @relation(fields: [familleId], references: [id])
   @@id([campagneId, id])
   id Int @default(autoincrement())  // couple produit/famille optionnels → pas

 }

 Workflow de statut (lib/marketingCampagneWorkflow.ts, nouveau)

 Calqué sur lib/dossierInterCommissionWorkflow.ts::appliquerActionDossier :
 - TRANSITIONS: Record<CampagneAction, StatutCampagne> (ex.
 SOUMETTRE→PLANIFIEE, APPROUVER→APPROUVEE, ACTIVER→ACTIVE,

 ARCHIVER→ARCHIVEE).
 - PRECONDITIONS: Record<CampagneAction, StatutCampagne[]> (statuts source

 - notifyRoles(tx, ["RESPONSABLE_MARKETING"], {...}) + auditLog(tx, userId,

 transition (§80 audit obligatoire).
 - Retourne la campagne mise à jour avec include (responsable, budget,
 objectifs).

 RBAC + Auth helper

 lib/authMarketing.ts (nouveau, calqué sur lib/authRPV.ts) :
 export async function getMarketingSession() {
   const session = await getAuthSession();
   if (!session) return null;
   const role = session.user.role, gRole = session.user.gestionnaireRole;
   if (role === "ADMIN" || role === "SUPER_ADMIN" || gRole ===
 "RESPONSABLE_MARKETING") return session;
   return null;
 }

 Routes API (app/api/admin/marketing/...)

 - campagnes/route.ts — GET (liste + filtres statut/type/agence/responsable),
 POST (création, statut initial BROUILLON, inclut le brief §9).
 - campagnes/[id]/route.ts — GET détail (avec budget, objectifs, agences,
 produits, canaux, audience, dépenses), PATCH (édition champs hors statut).
 - campagnes/[id]/action/route.ts — POST, appelle appliquerActionCampagne
 (transitions de statut).
 - audiences/route.ts — GET liste (avec tailleCalculee), POST création (règles
 + type statique/dynamique → calcule immédiatement les membres).
 - audiences/[id]/route.ts — GET détail (règles + aperçu échantillon de
 membres).
 - audiences/[id]/recalculer/route.ts — POST, force recalculerAudience() (utile
 aussi pour un futur cron §12 "chaque jour").
 - audiences/rfm/route.ts — GET, calcule et retourne les segments RFM courants
 (§14) sans forcément créer une audience persistée à chaque appel.
 - budgets/[id]/action/route.ts — POST (workflow DEMANDE→APPROUVE/REJETE, §54).
 - types-campagne/route.ts, canaux/route.ts — CRUD simple des référentiels
 paramétrables (§81, réservé à l'admin/responsable marketing).
 - stats/route.ts — GET, KPIs §3 (budget, dépenses, campagnes
 actives/terminées, nouveaux clients, CA/marge attribués via campagneId, CAC,
 ROI...) + parAgence (§4, tableau agence×budget×leads×clients×CA×ROI) — pattern
 scoping identique à app/api/rpv/ventes/route.ts (bypass admin, sinon
 restreint aux agences du gestionnaire pour
 CHEF_AGENCE/RESPONSABLE_POINT_DE_VENTE).
 - Alerte stock (§61) intégrée à la réponse de campagnes/[id] : pour chaque
 produit ciblé × agence ciblée, comparer StockSite.quantite à
 alerteStock/seuilCritique et renvoyer un tableau alertesStock.

 Toutes les routes protégées par requirePermission(session, "marketing",
 action) en plus de getMarketingSession().
