 Combler les trous CDC §51-56 (IA/OCR facture + comptabilisation automatique)
 Contexte

 L'audit du CDC §51-56 a montré :
 - §51 IA/OCR facture : absent (aucune extraction, aucune proposition d'imputation).
 - §52 Comptes sur fiche produit : absent (aucun champ compte* sur Produit/Famille/Catégorie).
 - §53 Cascade Produit>Catégorie>Famille>Config générale : partiel (le moteur RegleComptable existe mais la priorité est un entier libre, pas une vraie hiérarchie ; le niveau
 Famille est mort ; pas de niveau "config générale").
 - §54/§55 Générateurs vente/achat : partiels (mode paiement + catégorie + TVA déjà couverts ; "type client" et "point de vente" absents des conditions).
 - §56 Stock → Comptabilité : partiel — achat/vente/inventaire couverts, mais pertes/casses/dons, ajustements de stock et transferts ne génèrent aucune écriture, ce qui laisse
 exactement la divergence stock logiciel ≠ stock comptable que le CDC demande de fermer.

 L'utilisateur a validé de traiter les 6 points sans en prioriser un, et a choisi pour §51 une extraction heuristique locale (pdf-parse + regex), sans appel à une API IA externe
 (aucune clé configurée dans le projet, pas de coût récurrent).

 Le moteur comptable central (lib/comptabilite/moteur.ts) est déjà bien conçu : creerEcriture() (BROUILLON par défaut), resoudreRegleComptable() (RegleComptable DB > défaut
 code), compteAuxiliaireOuDefaut(), resoudreTvaVente/Achat(). Tout le travail consiste à enrichir ce moteur et les points d'intégration existants, jamais à le remplacer.

 Phase 3 — §56 : pertes, ajustements, transferts → comptabilité

 Constat additionnel (découvert en explorant app/api/magasinier/bons-sortie/[id]/route.ts)

 Le PATCH ne décrémente le stock QUE pour typeSortie ∈ {LIVRAISON_CLIENT, PERTE, CASSE} (L79, L144). Les types DON, VOL, CONSOMMATION_INTERNE, RETOUR_FOURNISSEUR tombent dans la
 branche "mise à jour standard" (L207) qui ne touche ni le stock ni MouvementStock — un bon de sortie de ces types-là ne fait aujourd'hui rien de réel. Il faut élargir la
 condition existante (L144) à tout typeSortie non-LIVRAISON_CLIENT, avant de brancher la compta dessus (sinon l'écriture comptabiliserait une sortie de stock qui n'a jamais eu
 lieu).

 Phase 4 — §51 : OCR facture heuristique (sans IA externe)

 Dépendance

 Ajouter pdf-parse (extraction de texte brut depuis un PDF, aucune clé API).

 lib/ocrFacture.ts (nouveau, pur/serveur)

 extraireDonneesFacture(buffer: Buffer): DonneesFactureExtraites — texte brut via pdf-parse, puis regex :
 - Montants : recherche de motifs TOTAL TTC, TOTAL HT, TVA suivis d'un nombre (formats FR 1 234,56 et 1234.56).
 - Date : motifs \d{1,2}[/\-.]\d{1,2}[/\-.]\d{2,4}.
 - Numéro : motifs (Facture|N°|Ref)\s*:?\s*[\w\-\/]+.
 - Fournisseur : heuristique sur les premières lignes non vides du document (en-tête) + tentative de correspondance contre Fournisseur.nom en base (au niveau de l'appelant, pas
 dans ce module pur).
 - Lignes : détection de lignes tabulaires désignation … quantité … prix … montant (best-effort, renvoie [] si non détecté plutôt que d'inventer des lignes).
 Chaque champ non détecté reste null — jamais de valeur inventée.

 Schéma

 Nouveau modèle PropositionImputationOCR : pieceJustificativeId Int @unique, champs extraits (fournisseurDetecte, fournisseurIdMatche, dateDetectee, numeroDetecte,
 montantHT/TVA/TTC, lignesJson Json?), compteDebitProbable/compteCreditProbable String?, statut ANALYSE|VALIDEE|REJETEE, ecritureCreeeId Int?, analyseParId/valideParId.

 API

 - POST /api/comptable/ocr/analyser { pieceJustificativeId } — télécharge le PDF depuis l'URL uploadthing de la pièce (déjà uploadée via l'endpoint justificatif existant,
 app/api/uploadthing/core.ts:59-82), appelle extraireDonneesFacture, tente le matching fournisseur, résout le "compte probable" via
 resoudreRegleComptable("RECEPTION_ACHAT_VALIDEE", …)/cascade Phase 1 si le fournisseur est identifié. Sauvegarde PropositionImputationOCR, statut ANALYSE. Ne crée aucune
 écriture.
 - POST /api/comptable/ocr/[id]/valider — le comptable a relu/corrigé les champs proposés ; body = valeurs finales. Crée l'écriture via creerEcriture(tx, { …, statut:
 "BROUILLON" }) — statut est câblé en dur à "BROUILLON" dans cette fonction, jamais paramétrable par l'appelant, pour que l'contrainte CDC ("l'IA ne valide jamais seule") soit
 imposée au niveau du code, pas seulement de la convention. Marque la proposition VALIDEE + ecritureCreeeId. L'écriture rejoint ensuite le circuit normal BROUILLON→VALIDE déjà
 existant (app/api/comptable/ecritures/[id]/route.ts), le comptable la valide comme n'importe quelle autre.
 - POST /api/comptable/ocr/[id]/rejeter — statut REJETEE, aucune écriture créée (facture mal reconnue, saisie manuelle classique).

 UI

 Sur la modale d'upload de pièce justificative (celle ouverte depuis "Journal des opérations", cf. commentaire dans app/dashboard/user/comptables/saisie/pieces/page.tsx:8-13) :
 bouton "Analyser (reconnaissance auto)" visible quand nature === "FACTURE" → appelle /ocr/analyser → ouvre une modale de relecture pré-remplie et éditable (fournisseur, date,
 montants, compte probable) avec deux actions : Créer l'écriture (brouillon) / Rejeter — saisir manuellement. Aucun bouton "valider directement" dans cette modale — la
 validation de l'écriture reste l'écran normal des écritures BROUILLON.

 besoin).

 validation OCR) via l'UI en dev et vérifier dans /dashboard/user/comptables/journaux que l'écriture BROUILLON apparaît, équilibrée, avec les bons comptes résolus selon la
 cascade Phase 1 (tester un produit avec compte spécifique, un produit sans compte propre qui hérite de sa catégorie, et un produit qui retombe sur le défaut global).

 en dernier recours).
